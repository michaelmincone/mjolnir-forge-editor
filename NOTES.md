Verified on this one real file (inspected with `xxd` and `shasum` only; nothing decoded beyond the first header bits):
- File is 59,392 bytes = the 29,481-byte plain 4-block map variant (SPEC 2.2) + **29,911 zero bytes of padding after `_eof`** (the spec's "trailer" case; must be kept verbatim).
- Blocks: `_blf` 0x30 v1.2, `chdr` 0x2C0 v10.2, `mvar` **0x7028 v31.1** at 0x2F0, `_eof` 0x11 v1.1 at 0x7318 with body value 0x7318 (BE).
- `chdr` holds content type 5 (map variant) and file length 0x7329 = 29,481 (LE) at 0x40/0x44.
- `mvar` block: SHA-1 at +12, **stored length at +32 = `00 00 33 FF` = 13,311 big-endian**, bit stream at +36 (file offset 0x314). First nibble = 6 (map variant stored +1) followed by 32 bits = 29,481 (the embedded fileLength): exactly the SPEC 3.2 header layout.
- **Hash recipe = `SHA1( LE32(L) || stream[0:L] )` with L = 13,311, no salt: reproduces the stored hash `b41f6cb0fabe27fc9b22a607c0a9c9ca51c344e3` exactly.** Salted-BE32 (the recipe verified on the game-variant samples), BE32-unsalted, payload-only and full-0x7000 variants do NOT match. So for an MCC-written map variant the flavour is **(length stored big-endian, hash input little-endian, no salt)** = SPEC `plain_le32`. The writer must reproduce the flavour detected on the template (SPEC 2.7 / binding decision D); the "salted fallback for an unmatched hash" must never be used for a file like this one.
Caveats: a single file from Dec 2019 (early MCC); its body (labels, 651 slots, quota table) has not been decoded yet, so the body layer remains unverified until the G3 reader is run on it.
Consequence for the plan: this file becomes tier **T3-real** (SPEC 9.1): the container/hash/length/trailer clauses are added to G1's tests, and the G3 body walk is first exercised on it. If the user supplies further real files (e.g. from `...\haloreach\map_variants\` on the Windows PC), put them in the same folder.

## D11. Real-file decode result and the quota decision (2026-10-10)
G3 decoded the real Breakneck file ("Headstrong", map id 10050) completely on the FIRST run with no tuning, and an independent decoder written from the spec text alone agrees on every field: header ends at bit 1,327; 651 slots of which 610 present (slots 0-609); 82 quota rows; the walk ends at bit 106,487 and ceil(106,487/8) = 13,311 equals the file's own stored length exactly; the 122,889 tail bits are zero; every slot re-packs bit-identically; unmodified and forced re-encode both reproduce all 59,392 input bytes. This is the first real-data evidence for the body layout (header, fixed body, label table, slot records, quota table, axis widths 23/23/23, flag8 vs plain8 undetermined because no type-19 object exists). Details: docs/mvar/notes/G3.md and real_mvar_0aaaf8c7.md.
Still unverified because the file has none of them: type-19 rule, v32 GUID block, parent links, out-of-bounds records, _cmp/_fsm shapes, the disputed placement bits, the orientation conventions (SPEC 4.6).
Facts that shape the star deliverable: the map already holds 610 objects, so only **40** can be added under the 650 limit; it contains NO Block objects and the quota rows of every Block folder are (min 0, max 0, placed 0) (it is a finished 343 matchmaking variant: maximum == placed on 39 of 42 non-zero rows). Structure/Scenery objects have cachedType 0 in this file (confirms the assumed-zero hint). One Fixed-physics placement byte (0x4C) exists in the file.
**DECISION D11 (orchestrator, for the owner):** adopt G3's option (b): a new opt-in export option `raise_quota_max` (default OFF) that, when a row's new `placed` would exceed its `maximum`, raises `maximum` to the new `placed` (never lowers anything, never touches `minimum`) and reports warning `W_QUOTA_MAX_RAISED` "quota maximum raised: unverified". Without the option the export is refused with E_QUOTA as in SPEC 5.4/7.5.
