## 2. Decisions (most reasonable choice made, work continued)

1. **Block: `Block, 1x1`**, chosen explicitly (`--block "Block, 1x1"`, so no silent fallback to another type; `auto` would also pick it).
   All 12 visible building blocks of Breakneck were measured (real library, read-only, hash checked before and after, same
   `measure_collection` the tool uses). Every one is palette folder 63, i.e. the same quota row 63 < 82, so the quota does not choose.
   The star is upright in the X-Z plane, so the face is width x height and the depth is the thickness:

   | Block | id | mesh box x * y * z |
   |---|---|---|
   | Block, 1x1 | 0x3F00 | 1.0182 * 1.0182 * 1.0000 |
   | Block, 1x1, Flat | 0x3F01 | 1.0176 * 1.0176 * 0.2000 |
   | Block, 1x1, Short | 0x3F02 | 1.0176 * 1.0176 * 0.5000 |
   | Block, 1x1, Tall | 0x3F03 | 1.0182 * 1.0182 * 2.5000 |
   | Block, 1x1, Tall And Thin | 0x3F04 | 0.5000 * 1.0000 * 3.0005 |
   | Block, 1x2 | 0x3F05 | 1.0182 * 2.0183 * 1.0000 |
   | Block, 1x4 | 0x3F06 | 1.0182 * 4.0155 * 1.0182 |
   | Block, 2x1, Flat | 0x3F07 | 1.0294 * 2.0000 * 0.2550 |
   | Block, 2x2 | 0x3F08 | 2.0000 * 2.0000 * 0.9999 |
   | Block, 2x2, Flat | 0x3F09 | 2.0000 * 2.0000 * 0.2550 |
   | Block, 2x2, Short | 0x3F0A | 2.0000 * 2.0000 * 0.4999 |
   | Block, 2x2, Tall | 0x3F0B | 2.0000 * 2.0000 * 3.0000 |

   (No 3x3 on Breakneck; the 11 invisible blocks, folders 70 to 80, are excluded: the star must be visible.) A good pixel needs
   a square face (width ~ height) and, so that an unverified quarter turn of yaw cannot change anything, a square plan (width ~
   depth); the smaller the block the finer the star. Only `Block, 1x1` is both; `Block, 1x2` has the right face but is 2 deep and not
   square in plan; the flat blocks would make a thin star only lying down or standing on edge, and a tilt is refused
   (`E_TILT_UNSUPPORTED`, SPEC 5.6); `Block, 2x2` is a 2:1 face. The spacing is the measured mesh box (1.0182 along x, 1.0 along z).
2. **Design: fixed 39-block `pixel39`** (new `--shape`), not the sampled grid. The task said to pick a 4-connected grid and cell count
   <= 40 or fix the layout. Of the sampled filled grids with <= 40 cells, 5, 6, 7, 8, 9 and 12 are face-connected (17, 16, 24 blocks
   for 7, 8, 9; 38 for 12) and none is a good star within 40 (grid 9 is small, grid 12 squat with a two-wide apex); grid 11 (34) is
   not face-connected (two feet touch a leg at a corner: 3 components under 4-connectivity, pinned in the new test). So a small
   search was made over
   area-coverage rasters of the true star polygon (columns 7 to 15, radius 4.5 to 7.4 rows, vertical phase, coverage threshold
   0.35 to 0.55, 6 x 6 sub-samples per cell, cell 1.0182 wide x 1.0 tall), keeping mirror-symmetric, 4-connected rasters with <= 40
   cells and ranking them by overlap with the true star: the best (0.83) is `pixel39` (9 x 9, radius 6.0 rows, centre 5.7 rows above
   the bottom of a 13-row grid, threshold 0.5). 39 blocks leave one free slot (649 of 650). Alternatives looked at: 40-block 9 x 10
   (three-block apex, feet on the legs; fills every slot, 650 of 650), 40-block 11 x 9 (thin T-bar arms), 40-block 9 x 9 with a
   solid 5-wide body (reads as a house). The unit test re-derives the literal from the rule, so it is not a free-hand drawing.
   A render of the decoded file shows a clear five-pointed star (apex up, two arms, two legs).
3. **Placement** (`tools/star_placement.py`, reads the template's decoded records read-only). The file has no terrain, so room is
   measured against the 610 objects and the 17 boundary volumes. Measures: `xy` = horizontal distance of the star's footprint to the
   nearest object (any height), `3d` = box-to-point distance, `volume` = distance to the nearest kill / safe boundary (a box volume
   is overestimated by its horizontal bounding circle `hypot(width / 2, length / 2)` because its yaw is not known; a cylinder by
   its radius; vertical extent `[z - bottom, z + top]`), `hull` = how far inside the convex hull of the objects the footprint is
   (the stand-in for "the playable region"; the file's bounds are +-20000 on every axis).
   * **The map is full.** The best a 9.16 x 1.02 strip can do in plan, among places at least 3 inside the hull and at least 3 from
     every volume and object in 3-D, is **2.59** from the nearest object. The pure largest empty circle among the objects (centre
     3 inside the hull) has radius 5.79 at (6.71, 5.99); that circle is not the star's footprint (a 9.2 strip centred there is only 1.53
     from an object in plan), so it was not used. The corners of the bounding box (r 18.4 at (-28.8, -29.0) and so on) are outside
     the hull (outside the map).
   * **Height.** The objects span z 2.10 to 21.70 (median 5.40); floors are at about z 2 to 3.6 (low ground), 5.2 to 5.4 (mid), 7 to 8,
     10.4 (a west platform), and the structure at (-10, -20) is at 11 to 12.4. Objects above z 15 are boundary volumes only.
     So the star is separated from the objects by height: top = the highest object (21.698) rounded down to a 0.25 grid = **21.5**
     (inside the vertical range, not beyond it), bottom 12.5.
   * **Chosen:** centre (13.25, -15.75, 17.0) (the search found (13.206, -15.758); rounded to 0.25). Numbers measured on the
     DECODED output (`star_placement.py measure`): xy 2.590 (Flag Stand, slot 425, at (15.61, -18.85, 5.21)), 3d 7.738 (the same),
     volume 3.873 (Soft Kill Boundary, slot 592, at (20.40, -8.30), z from 10.8 up), hull 9.314, objects inside the star's box 0,
     overlapping blocks 0 (beyond the position step). The nearest eight objects in 3-D are 7.7 to 8.2 away (all ground-level
     objects at z 5.2 to 5.4 or the boundary 592). Its x range is 8.668 to 17.830, y -16.261 to -15.243, z 12.501 to 21.502.
   * Worst case for the volume: if a boundary box's width / length were half extents rather than full extents (Forge's editor shows
     them as full sizes; the file semantic was not verified), slot 592 would be 1.6 from the star, still outside. If its yaw
     were axis-aligned the distance is 4.0 or 6.4.
   * Runner-ups (same star, same height): (13.706, -15.883) xy 2.46; (-3.794, 14.867) xy 2.39 but 3d 4.62 and volume 3.18.
   * Not knowable here: whether terrain or a structure occupies the spot (the objects around sit 7 to 9 below the star: 103 objects
     within 12 units, z 3.5 to 8.1).
4. **Limits through the same validation as every export**: stock map, stock object, 649 <= 650, positions inside the bounds, rotation
   gate (E_ROTATION_GATED without it), quota row 63 -> `(0, 39, 39)` via the D11 option with `W_QUOTA_MAX_RAISED` (without the
   option the export is `E_QUOTA`: tested by G5), budget words unchanged (spent 3,885 of 10,000, `I_BUDGET`: cannot be recomputed
   offline; 6,115 are free, so 39 blocks overspend only if each costs more than 156: not measured, not claimed).
5. **Everything plain**: `--provider real` (default), `--real-library`, no `--color` (no colour written: team colour), no label,
   flags: the template holds no block, so the placement byte is the library's `0x0C` with the physics bits replaced: `0x4C` (the
   byte of the one Fixed object already in the file, a crate), team neutral (9), class 0 assumed (`W_CACHED_TYPE_ASSUMED`: Structure
   group).
6. **Yaw as written**: raw angle code 12288 on all 39 (Blender rotation 0 = forward +Y = yaw pi/2 in SPEC 4.7), a quarter turn from
   the 8192 that most objects of the file carry. The star tool's caveat text says "pure yaw 0" (Blender's yaw 0): imprecise in
   file terms (the file's zero is 8192). A quarter turn of a square-plan block is invisible, which is one more reason for `Block,
   1x1`. Left as it is: the printed caveat of the star tool is not pinned elsewhere and changing it would change the log of an
   already kept file; the report says the exact code.
7. **Output files**: `Headstrong_Star.mvar` in `~/Documents/Halo_MCC/mjolnir-forge-editor/forge-workspace/maps/headstrong-star/` (created; outside the repo, not beside any
   original, not in a sample folder). The build wrote `Headstrong_Star.mvar.report.txt` beside it (the star tool does that for a kept
   file). Never overwritten; `--overwrite` not used.
8. **Extra: `Headstrong_Unchanged_Resave.mvar`.** The ladder asks for "step 1: load the unchanged re-save". A no-op export through the
   plugin (import, export, no edits) is byte-for-byte the original (passthrough, SPEC 5.2; sha256 `e514a53b...79bb254`, checked in the
   run, 610 objects imported, 0 warnings, 0 changes), made through the plugin's own operators so that the control file really is
   "what the plugin saves". Both files carry the title "Headstrong": the report tells the owner to load them one at a time.
9. **Not done on purpose**: the star was not placed with the Blender GUI; the `--center` was given explicitly (the search is a

## 4. Mistakes found on the way

* **The star tool's default star (34 blocks) has detached feet** (known from S1prep, pinned): fixed for the deliverable by the design.
* **A false failure in the new checker**: the first version counted any overlap of decoded positions, which are rounded to the file's
  position step (0.00477), as an overlap (35 pairs "overlap" by up to 0.0034). Now a pair overlaps only beyond two steps; the line
  prints the deepest overlap. `star_placement.py measure` had the same bug (an exact 1e-6 tolerance on decoded positions); fixed
  with the real step (from the file's bounds and axis bits).
* The first draft of the `measure` command used half the library's `position_tolerance` as "the step" (0.0067); corrected to the
  true 40,000 / 2^23 = 0.00477.
* Two of my first tamper tests flipped the wrong stream bit (the span tuples are `(name, start, end)`); the failures showed it. Fixed.

## 5. Spec and pipeline gaps found (section numbers)

1. **5.4 / 7.5 vs the real map** (also G3 / D11): a finished matchmaking variant allows exactly what it holds, so any addition
   needs the D11 option; the star carries `W_QUOTA_MAX_RAISED`. Whether MCC honours or rebuilds the maximum is unknown (SPEC 10.2).
2. **8.5 / S1prep gap 2** (still open): no structured result from the export operator; the star tool parses the report text.
3. **3.9 / 5.6**: a block in a template with no block of its type: class 0 and the placement byte are assumed (the report says so);
   there is no way to test it except in the game (ladder rung 3).
4. **4.7 / DEC-4.8 wording**: "pure yaw 0" in the star tool's caveat is Blender's zero; the file code is 12288 (section 2.6).
5. **Boundary box dimensions**: the library decodes `width`, `length`, `top`, `bottom` of a box shape; the spec does not say whether
   width and length are full or half extents. `star_placement.py` assumes full and overestimates by the bounding circle; the unit
   tests pin the numbers on the real file under that assumption.
6. **`map variant bounds` vs "centred in the map"** (S1prep gap 4, still true): the middle of the bounds is the origin only
   because Breakneck is centred there; the star tool takes `--center`, and this run passed it.
7. **SPEC 9.5 rung 3** wants a single added block; no tool makes it (the star tool's smallest is a 20-block outline, `--cells 9 --outline`).
   The report says how to make one in Blender by hand.
